One backend service, built in public over six months

A plan to return to hands-on backend engineering, built around a Python service on AWS and finished when it has load-test numbers anyone can check.

Plan written 31 October 2026. Window: November 2026 to April 2027. The project is in progress, so everything below is a plan, not a result, until the milestones say otherwise.

Open the progress tracker, a checklist, board and problem list for the same plan. Ticks are saved in your own browser.

The project

playback-config-service serves per-title playback configuration (which streams, which features) filtered by what a given account is entitled to, and collects playback telemetry events behind a queue. It is the kind of service a streaming backend team runs, small enough to finish and real enough to have trade-offs worth writing about.

Language
Python 3, FastAPI, type-checked
Runtime
ECS Fargate behind an Application Load Balancer
Data
PostgreSQL on RDS, Redis on ElastiCache
Async
SQS with a worker that batches writes
Delivery
Terraform for all infrastructure, containerised builds, CI/CD pipeline
Operability
Structured logs, metrics, alarms, a short runbook

Definition of done: a public URL, a load-test report with real request rates and latency percentiles, and a README that explains what was measured, what broke, and what changed as a result. Numbers go in this page when they exist.

Six months, one test per month

About 8 to 10 hours a week, roughly 210 hours in total. Each month has one pass/fail check so progress is visible and not just felt.

  1. Nov
    Writes a hash-map solution with no syntax lookup.
    Python fluency, first algorithm sets, project repo and infrastructure skeleton.
  2. Dec
    The service returns entitlement-filtered data from PostgreSQL.
    Data model, indexing, transactions, the first working endpoints.
  3. Jan
    A URL anyone can open, with load-test numbers.
    Caching, queue and worker, deployment, load testing and tuning.
  4. Feb
    The API layer exists in both Python and TypeScript.
    A bounded port of the API to Node and TypeScript (see market findings), applications begin.
  5. Mar
    Four or more real phone screens completed.
    Mock interviews, system design practice, behavioural stories.
  6. Apr
    A signed offer.
    Onsite loops and negotiation.

The skills track

Algorithms and Python

120 problems, chosen for patterns that show up in backend interviews: hash maps, two pointers, trees and graphs, heaps, intervals, basic dynamic programming. The goal is fluency, so problems are re-solved from a blank file after a week.

System design

About 40 hours, shaped by the syllabus that real job postings imply (below). Each topic ends with a written design for something small enough to build, and several are built into the project.

What the postings ask for

  • REST and GraphQL API design
  • SQL and NoSQL modelling, indexing, transactions
  • Caching, with Redis named most often
  • Queues and asynchronous processing
  • AWS in production, containers, CI/CD, infrastructure as code
  • Observability and on-call practice

What the market actually asks for

The plan starts from data. A search of 54 "Software Engineer II" postings in media, gaming and entertainment, as of 31 October 2026, found:

  • Only 4 are genuine backend roles. The rest are frontend, mobile, data, QA or similar under the same title.
  • "II" is not a consistent level. Years of experience asked ranged from "up to 2" to "5+" across the backend roles.
  • None names Python. Three of the four name Node or TypeScript first. That is why February includes a bounded port of the API layer: the resume should match what screens look for, and the underlying skills transfer.
